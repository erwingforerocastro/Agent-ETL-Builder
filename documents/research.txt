## 1. What this project is today

Agent ETL Builder is a local FastAPI service that executes structured, validated ETL plans built
from a fixed allowlist of pandas functions. It can also inspect a workspace data file, return an
assessment report, confirm that report into a pipeline plan, and use a local Ollama model to turn
a natural-language request into a validated plan.

The beta is a **deterministic validated-plan engine with a local LLM intake**:

- the model produces only a transformation draft, constrained by a registry-derived JSON schema;
- source and destination operations are bound deterministically from explicit file extensions;
- the existing plan validator is the final gate;
- execution still runs only validated plans through the allowlisted interpreter;
- LangGraph is installed and `infrastructure/state/checkpointing.py` exposes an `InMemorySaver`
  adapter, but the run workflow does not use it;
- there is no remote model provider, tool-calling loop, or generated-code execution.

Supported entry paths:

```text
structured plan -> validate -> approval? -> execute
source only     -> assess  -> confirm destination -> validate -> approval? -> execute
message + paths -> bind -> sample schema -> Ollama draft -> validate/repair -> approval? -> execute
```

## 2. Runtime in one picture

```text
uvicorn main:app
  |
  +-- interfaces/api/app.py
  |     +-- /health
  |     +-- /runs ... -> application/use_cases/run_manager.py
  |     +-- optional X-API-Key and Content-Length middleware
  |
  +-- RunManager (one per process)
  |     +-- parse plan -> PlanValidator
  |     +-- choose intake: assessment, natural-language, or submitted plan
  |     +-- RunWorkflow (one instance per run; run state machine)
  |     +-- ThreadPoolRunScheduler (4 workers) -> background execution
  |     +-- InMemoryRunCheckpoint, JsonlRunLog over InMemoryRunLog, in-memory outcomes
  |
  +-- ExecutePlanUseCase -> RegistryStepRunner -> ModuleRegistry
  |                                              -> SandboxExecutor
  |                                              -> allowlisted pandas function
  |                    -> JsonlRunLog + CsvTransformLog
  |
  +-- AssessSourceUseCase -> WorkspaceSourceReader
                           -> ProfileSourceUseCase -> PandasChunkProfiler
                                                   -> FilesystemProfileWriter
  |
  +-- NaturalLanguagePlanIntake -> WorkspaceSourceSchemaProbe
                               -> OllamaPlanSynthesizer -> local Ollama /api/chat
  |
  +-- PostgresTableLoader (adapter only; not a registry destination)
```

`src/main.py` is the only composition root. It sets:

- workspace = `Path.cwd()`;
- artifacts root = `<cwd>/artifacts`; logs root = `<cwd>/logs`;
- registry = `MODULE_SPECS` plus `MODULE_FUNCTIONS`;
- default sandbox = 60 seconds, 512 MB, no network, workspace-only;
- four background workers;
- `OllamaPlanSynthesizer` and `NaturalLanguagePlanIntake` only when
  `AGENT_ETL_OLLAMA_MODEL` is set.

## 3. The three supported entry paths

### A. Structured plan

The request must contain `message` or `plan`.

1. The plan is parsed by strict Pydantic (`extra="forbid"`).
2. `run_id` and `mode` must match when also supplied in the request.
3. The full validation pipeline runs.
4. A valid plan that needs no approval becomes `ready` and is scheduled.
5. A plan with writes or `approval_required: true` becomes `awaiting_approval`.
6. `POST /runs/{id}/approve` with `approved: true` moves it to `ready` and schedules it.
7. Before each execution attempt the workflow re-checks registry version, run id, mode, plan
   hash, and revalidation.
8. Execution runs source, transformations, then destination through the sandbox.

`approved: false` terminates as `rejected`.

### B. Source-only assessment

The request supplies `source` and no `plan` or `destination`. The API schema still requires
`message` or `plan`, so a source-only request needs a `message` (for example, "Assess this file").

1. `RunManager` selects `AssessmentPlanIntake` instead of submitted or natural-language intake.
2. `WorkspaceSourceReader` resolves a workspace-confined file and hashes its bytes.
3. `AssessSourceUseCase` runs a full scan in chunks inside the sandbox.
4. `ProfileSourceUseCase` writes per-chunk records, a quality CSV, and an info JSON.
5. The run becomes `awaiting_clarification` with the assessment attached and
   `next_action: "confirm"`.
6. `POST /runs/{id}/confirm` with `{"destination": "..."}` builds a fixed `save_csv` pipeline
   plan from the draft, rejects a destination that normalizes to the source path, validates the
   plan, and moves the run to `awaiting_approval`.
7. Approval executes the plan normally.

Supported source files: `.csv`, `.json`, `.jsonl`, `.ndjson`, `.parquet`, `.pq`.

`mode: "assessment"` is inspection only: it returns the report, reports
`next_action: "provide_plan"`, and `confirm` returns `409`. Assessment mode always selects the
assessment intake, even if a destination is supplied or the source is missing. A destination is
ignored and called out in the questions; a missing source becomes a clarification question.

### C. Natural-language pipeline

This path is active when `AGENT_ETL_OLLAMA_MODEL` is set.

1. `RunManager` selects `NaturalLanguagePlanIntake` when no plan is supplied and the request is
   not source-only.
2. The intake binds source and destination operations from the explicit path extensions:
   `.csv` -> `read_csv`/`save_csv`, `.json` -> `read_json`/`save_json`,
   `.jsonl`/`.ndjson` -> `read_jsonl`/`save_jsonl`, `.parquet`/`.pq` -> `read_parquet`/`save_parquet`.
3. Missing or unsupported paths become clarification questions. A destination that normalizes to
   the source path is rejected with a question.
4. `WorkspaceSourceSchemaProbe` reads the first 50 rows through `WorkspaceSourceReader` and keeps
   only column names and dtypes. Source values are not sent to the model.
5. `OllamaPlanSynthesizer` sends a system prompt, conversation history, source/destination paths,
   the sampled schema, and a registry-derived JSON schema to `POST /api/chat` with
   `stream=false`, `format=<schema>`, `temperature=0`, and a bounded `num_predict`.
6. The model returns `name`, `description`, `transformations`, `questions`, and
   `missing_inputs`. It cannot output source/destination operations, step IDs, unknown
   operations, or extra parameters.
7. The intake assigns `s1..sn`, removes empty/None optional parameters, binds the explicit
   source/destination, and parses the full plan.
8. `RunIntakeCoordinator` validates the plan. A validation failure is fed back to the model as
   `previous_error`; the attempt budget is the normal 3 clarification attempts. Exhaustion
   terminates the run with the validation error.
9. A valid plan moves to `awaiting_approval`. Approval executes it through the sandbox.
10. If the model asks for columns or values, the run stays in `awaiting_clarification` with
    `next_action: "clarify"`. `POST /runs/{id}/messages` resumes the same intake with a bounded
    12-turn history.

The model is local-only in the beta. Plan generation is synchronous and usually takes 15-45
seconds with `llama3.1:8b`. If Ollama is unavailable, times out, returns HTTP errors, invalid
JSON, empty content, or an oversized response, the run terminates with a `PlanSynthesisError`
code such as `PLAN_SYNTHESIS_UNAVAILABLE`, `PLAN_SYNTHESIS_TIMEOUT`, or
`PLAN_SYNTHESIS_INVALID`.

A request with `source` and `destination` but no plan is handled by the natural-language intake.
A path mentioned only inside message text is not detected; `source` and `destination` must be
explicit. When natural-language planning is disabled (`AGENT_ETL_OLLAMA_MODEL` unset), a
plan-less request falls back to the submitted-plan intake, which explains how to enable the
agent in its clarification message.

## 4. Actual HTTP API

| Method | Path | Behavior |
|---|---|---|
| `POST` | `/runs` | Create a run from a message, source-only request, natural-language request, and/or plan. Returns `201`. |
| `GET` | `/runs/{run_id}` | Current run state, plan, assessment, result, cleanup, next action. |
| `POST` | `/runs/{run_id}/confirm` | Supply a destination for an assessment draft. |
| `POST` | `/runs/{run_id}/messages` | Continue a clarification run with `{"message": "..."}` and optional `source`/`destination`. |
| `POST` | `/runs/{run_id}/approve` | `{"approved": true\|false}`. |
| `POST` | `/runs/{run_id}/cancel` | Cancel at the next safe boundary. |
| `GET` | `/runs/{run_id}/logs` | Redacted in-memory lifecycle and step events. |
| `GET` | `/health` | Service metadata and `plan_generation` (`ollama` or `disabled`); public even when an API key is configured. |

`next_action` is one of `provide_plan`, `clarify`, `confirm`, `approve`, `wait`, or `none`.
`clarify` means the client should send `POST /runs/{id}/messages`; assessment pipeline runs use
`confirm`; assessment-only runs use `provide_plan`.

There is no generic resume endpoint beyond `/messages` and assessment confirmation. A run whose
workflow is lost on restart cannot be continued; create a new run.

Errors use `{code, message, retryable, details?}`:

- `PlanValidationError` -> `400`;
- `RunNotFoundError` -> `404`;
- conflicts such as invalid state, approval rejected/timeout, cancelled, stale plan -> `409`;
- request validation, including an empty `plan: {}` -> `422`;
- registry, sandbox, workflow, and unexpected errors -> `500`;
- a `PlanSynthesisError` raised outside intake -> `503`. A synthesis failure during intake
  terminates the run with the same error code and a `201` run response whose `status` is
  `failed`.

If `AGENT_ETL_API_KEY` is set, every `/runs` request needs `X-API-Key`; `/health` stays public.
The request-size check only inspects the `Content-Length` header.

## 5. Module allowlist

Registry version: `1.0.0`. Only these operations can appear in a plan:

| Kind | Module | Notes |
|---|---|---|
| Read | `read_csv` | Workspace file, pandas CSV options limited to current signature. |
| Read | `read_json` | JSON array/document. |
| Read | `read_jsonl` | JSON Lines. |
| Read | `read_parquet` | Single Parquet file, requires pyarrow. |
| Transform | `drop_duplicate_rows` | Not chunkable; subset + keep first/last. |
| Transform | `drop_empty_rows` | Chunkable; configured subset. |
| Transform | `trim_whitespace` | Chunkable; leading/trailing/both. |
| Transform | `standardize_column_names` | Chunkable; lower/upper/preserve, collision-safe. |
| Transform | `cast_column` | Chunkable; string/integer/float, raise/coerce. |
| Transform | `filter_rows` | Chunkable; one literal predicate per step; destructive. |
| Transform | `fill_missing_values` | Not chunkable; constant, mean, median, or mode; nulls only. |
| Transform | `normalize_dates` | Chunkable; parse with mixed formats and format with strftime; coerce is destructive. |
| Transform | `change_text_case` | Chunkable; lower/upper/title on selected or all text columns. |
| Transform | `replace_values` | Chunkable; exact text replacement; `new=null` is destructive. |
| Write | `save_csv` | Atomically overwrites a UTF-8 CSV file. |
| Write | `save_json` | Atomically overwrites a JSON array (`orient="records"`). |
| Write | `save_jsonl` | Atomically overwrites JSON Lines. |
| Write | `save_parquet` | Atomically overwrites Parquet; requires pyarrow. |

Startup rejects duplicate module names, a spec with no bound callable, and a bound callable with
no spec. There are no database modules in the allowlist.

The natural-language JSON schema is derived from this registry and contains only the ten
transformation modules. It excludes source and destination operations, pipeline `df` inputs,
path parameters, and any unknown properties.

## 6. Validation pipeline

`PlanValidator` runs these checks in order:

1. `SchemaValidator` - plan shape, mode, unique step ids, operation syntax.
2. `RegistryEntryValidator` - every operation is allowlisted; assessment plans are read-only.
3. `OperationRoleValidator` - sources are read-only and do not require a pipeline DataFrame;
   transformations require one and have no declared side effects; destinations write.
4. `ArgumentValidator` - argument names, required values, types, constraints.
5. `TransformationContractValidator` - transformation operations must be idempotent; filter,
   imputation, and date steps enforce cross-parameter rules.
6. `PlanPathValidator` - path shape and workspace confinement.
7. `LimitsValidator` - step count, chunk size, serialized plan size.
8. `SecurityValidator` - no code/raw SQL, credentials, NaN/infinity, excessive depth/strings.
9. `ApprovalValidator` - write/destructive plans must set `approval_required: true`;
   assessment plans may not contain them.

Role and transformation-contract failures use `PLAN_INVALID_OPERATION_ROLE`,
`PLAN_NON_IDEMPOTENT_TRANSFORMATION`, or `PLAN_INVALID_ARGUMENT`. Confirmation and natural-language
intake validate the generated plan again. Execution validates again before running.

Plan validation still cannot inspect the source schema. The natural-language prompt receives a
50-row column/dtype sample, but column existence, dtype compatibility, and all-null behavior are
checked by the transformation modules during execution. Plan-time schema-aware validation is
deferred (`TRN-7`).

## 7. Run lifecycle

States:

```text
created -> awaiting_clarification -> ready -> running -> retrying -> succeeded
         -> awaiting_approval -> ready / rejected / timed_out
         -> failed / cancelled
```

Terminal: `succeeded`, `failed`, `rejected`, `cancelled`, `timed_out`.

Approval states: `not_required`, `pending`, `approved`, `rejected`, `timed_out`, `cancelled`.

- `awaiting_approval` requires `pending`.
- `ready` requires `not_required` or `approved`.
- `rejected` requires `rejected`.
- clarification is bounded to 3 attempts. `POST /runs/{id}/messages` resumes the same intake.
- execution allows at most 2 retries after the first attempt, with backoff 0.5, 1.0, capped at
  5 seconds. Only errors marked retryable are retried.
- cancellation is checked at approval, step, and retry boundaries. A running step is bounded by
  the sandbox timeout, not interrupted mid-step.
- non-success terminal paths apply `AGENT_ETL_CLEANUP_POLICY`. The default `cleanup` removes
  partial artifacts but preserves `artifacts/<run_id>/transform_log.csv`; `retain` keeps
  everything. Successful runs keep their artifacts.

## 8. Assessment behavior

- Assessment is synchronous during `POST /runs` and the whole operation runs under the sandbox.
- Full scan, default chunk size 10,000 rows.
- Profile metrics: column/row/dataset completeness, duplicate rows, uniqueness, numeric
  mean/median/mode/min/max/non-finite counts, datetime min/max/range, categorical frequencies.
- Accuracy is `N/A`; consistency and validity are `N/A` until declared rules exist.
- Finding codes: `SOURCE_EMPTY`, `DUPLICATE_ROWS`, `COLUMN_ALL_NULL`,
  `COLUMN_MISSING_VALUES`, `NON_FINITE_NUMERIC_VALUES`, `COLUMN_DISTINCT_CAPPED`,
  `COLUMN_FREQUENCY_TRUNCATED`, `PROFILE_APPROXIMATE`.
- Draft transformations are deliberately conservative:
  - duplicates detected -> `drop_duplicate_rows` over all columns, keep first;
  - any column name not snake_case -> `standardize_column_names` with `case=lower`.
- No other transformation is proposed. The missing input is `destination`.
- Assessment responses contain absolute artifact paths produced by the filesystem writer.
- `mode: "assessment"` always selects the assessment intake. It is read-only: a supplied
  destination is ignored and the questions say so, and a missing source becomes a clarification
  question. `mode: "assessment"` cannot be confirmed into a pipeline.

The natural-language source schema probe is separate from assessment: it resolves the source,
computes the normal content hash, and reads only a bounded first chunk for column names/dtypes.
It does not profile or expose values. The full-file content hash can add latency on large
sources.

## 9. State, artifacts, and logs

- `InMemoryRunCheckpoint` stores immutable run snapshots in a process-local, thread-safe dict.
  Restart loses all runs.
- `RunManager` also keeps workflows, outcomes, conversations, in-memory log entries, and a
  scheduled-id set in memory for the process lifetime; there is no eviction or retention bound.
- Profiling artifacts:

```text
artifacts/<run_id>/<source_id>_<source_type>_quality.csv
artifacts/<run_id>/<source_id>_<source_type>_info.json
artifacts/<run_id>/<source_id>_<source_type>_profile_chunk_<index>.json
```

- Monitoring artifacts:

```text
logs/<run_id>.jsonl
artifacts/<run_id>/transform_log.csv
```

- `JsonlRunLog` wraps `InMemoryRunLog`. Every event is redacted and appended to the JSONL file;
  the in-memory copy serves `GET /runs/{id}/logs`. If the file cannot be written, the event is
  printed to stderr and the run continues.
- `CsvTransformLog` writes one row per transformation step with columns
  `ID, Filename, Chunk, Prev_Step, Step, Date, Result, Error, Warnings`. Result/error/warnings are
  JSON-encoded; cells beginning with `=`, `+`, `-`, `@`, tab, or carriage return are prefixed
  with `'`; failures fall back to stderr.
- `ExecutePlanUseCase` emits `source_started`, `source_finished`, `step_started`,
  `step_finished`, `step_failed`, `destination_started`, and `destination_finished` events. It
  passes `run_id` through `ExecutionPort`; event context contains row counts, durations, step
  IDs, and sanitized errors, never raw rows.
- Redaction covers secret-looking keys (`password`, `token`, `api_key`, `authorization`, `dsn`,
  etc.), DSN credentials, bearer tokens, and `password=`-style assignments. It is applied to both
  monitoring adapters.
- Profiling artifact writes use a temporary file plus replace. `save_csv`, `save_json`,
  `save_jsonl`, and `save_parquet` use the same atomic temp-file-plus-replace mechanism.
- `PostgresTableLoader` is an adapter with transactional insert/upsert/truncate-insert modes.
  It requires an existing table and is not exposed as a plan destination because registry
  execution still denies network access.
- Log rotation, retention, and cross-process locking are not implemented; the beta assumes one
  writer per run.
- The LangGraph `InMemorySaver` adapter exists but is not used by the application.

## 11. Verified gaps and limitations

Natural-language planning:

- Local Ollama only; there is no OpenAI or other remote provider, tool-calling loop, or model
  fallback.
- Plan generation is synchronous inside `POST /runs` and usually takes 15-45 seconds with
  `llama3.1:8b`. There is no generating state or background job.
- The source schema is sampled from the first 50 rows. It is prompt context, not a plan-time
  schema contract; column/dtype errors are caught during execution.
- Source and destination must be explicit fields. Inline path extraction from message text is
  not implemented.
- Conversations are process-local, bounded to 12 turns, and lost on restart. A workflow cannot
  be resumed after a process restart.
- The model can still choose a valid but semantically wrong transformation. The approval step is
  the human control; there is no plan-quality evaluator beyond validation.
- Prompt injection and plan-quality regression tests are present but not exhaustive.
- No per-run model/prompt version or token/cost lineage is recorded.

Planning and API:

- No LangGraph graph/tool loop; only the unused checkpoint adapter exists.
- No Python project or code export; optional fixed-template export is deferred (`EXP-1`).
- Source-only requests need an explicit `source` plus a `message`; inline paths are not parsed.
- Profiling is only reachable through assessment; there is no standalone profiling endpoint.
- Confirmation accepts only a destination. Draft transformations cannot be edited and only
  `save_csv` is supported.
- Assessment-only mode cannot be confirmed into a pipeline.
- `next_action` is `clarify` for clarification runs; clients must use `/messages`, not a generic
  resume endpoint.

Execution and data:

- Ten transformation modules exist. The ordered plan step list is the v1 transformation DSL;
  plan validation enforces operation roles, idempotence, no transformation side effects, and
  cross-parameter rules. There are no multi-condition/OR filters, regex replacements,
  multi-column imputation steps, explicit date input formats, or mixed-timezone normalization
  yet.
- Plan validation cannot inspect the source schema. Column existence, dtype compatibility, and
  all-null behavior are checked by transformation modules during execution. Plan-time
  schema-aware validation is deferred as `TRN-7`.
- File destinations are `save_csv`, `save_json`, `save_jsonl`, and `save_parquet`. All are
  atomic overwrite writers. Append mode, compression/encoding options, parent-directory
  creation, and cross-process file locking are not implemented.
- `filter_rows`, `normalize_dates` with `errors="coerce"`, and `replace_values` with
  `new=null` are classified as destructive and require approval; assessment plans reject them.
- A transactional PostgreSQL table loader exists at the adapter level with insert, upsert, and
  truncate-insert modes. It requires an existing table; automatic table creation, type mapping,
  and schema-drift handling are deferred (`LOD-3`). It is not a registry destination because
  registry execution denies network access (`DB-2`).
- Load lineage, checksums, and load artifacts under `artifacts/<run_id>/` are not implemented;
  they are deferred to `LOD-5`.
- PostgreSQL read code exists, but no database module is in the registry allowlist. Registry
  execution also denies network access, so validated plans cannot read PostgreSQL yet (DB-2).
- Assessment covers workspace files only; no database assessment.
- Assessment is synchronous and full-scan; no sampling, cache, timeout, or background progress.
- Source content is not re-checked between assessment and confirmation/execution.
- An empty source can still be confirmed into a vacuous load.

Operations:

- All run state, outcomes, conversations, in-memory logs, approval decisions, and scheduling are
  single-process and in-memory. Multiple workers or a restart lose state and do not coordinate.
- JSONL and transform CSV files persist, but there is no rotation, retention, or cross-process
  locking.
- Approval timeout is only enforced by `RunApprovalCoordinator.wait`, which runs when
  `RunWorkflow.run()` waits on a pending approval. The API schedules only `ready` runs, so a run
  left in `awaiting_approval` stays there until approved or cancelled; no API timer expires it.
  Tracked as `WF-2` in `documents/backlog_v2.txt`.
- Rate limiting and CORS are not implemented. Authentication is a single optional API key.
- The request-size check trusts the `Content-Length` header.
- Execution responses do not include DataFrame rows; they expose `data_available` only.
- The sandbox is an in-process Python guard, not an OS container. Native extensions, CPU quotas,
  hard OOM enforcement, and timeouts blocked in native code remain outside it.
- `pandas` is pinned to `3.0.6`; `pyarrow` is required for Parquet.
- The runtime used for verification was Python 3.14.5, while `pyproject.toml` targets Python 3.12
  and type-checking is configured for 3.12.

## 14. Maintenance procedure

Update this file when any of these changes:

- a route, request/response field, status code, or next action;
- a run state, transition, approval rule, retry, or cleanup behavior;
- a registry module, source format, loader, or transformation;
- validation checks, limits, security rules, or path policy;
- composition-root wiring, workspace/artifact/log location, sandbox limits, or settings;
- persistence, logging, scheduling, or concurrency behavior;
- the natural-language provider, prompt, schema, model defaults, or repair policy;
- implemented/deferred status of a backlog item;
- dependencies, supported Python version, or verification baseline.

Checklist:

1. Inspect the changed code and its tests; do not rely on planning docs.
2. Run the verification commands and record the new baseline.
3. Update the affected sections and the "Last verified" block.
4. Move newly discovered complex edge cases to `documents/backlog_v2.txt`.
5. Never describe a planned feature as working.
