## Risks

- In-memory checkpoints do not survive process restarts; v1 has no crash resume.
- The v1 sandbox is an in-process guard proven on Windows; OS-level isolation, hard CPU/OOM
  enforcement, and process cleanup remain hardening items.
- WF-1 cancellation is honored at step, retry, and approval boundaries; a currently running
  step is bounded by the sandbox timeout rather than interrupted mid-step.
- Workflow checkpoints are in memory only. Restarting the process loses active runs and has
  no crash resume in v1.
- Approval timeout defaults to 300 seconds and is configurable with
  `AGENT_ETL_APPROVAL_TIMEOUT_SECONDS`; cleanup is configurable with
  `AGENT_ETL_CLEANUP_POLICY=cleanup|retain`.
- Filtering rows, coercing date parsing, and replacing values with null are destructive and
  require approval; assessment plans reject them.
- Plan validation is schema-agnostic: column existence, dtype compatibility, and all-null
  behavior are checked during execution. The natural-language prompt receives a 50-row schema
  sample, but the plan itself is not validated against it. Plan-time schema-aware validation is
  v2 `TRN-7`.
- Natural-language planning requires a running Ollama server and a capable local model. Model
  quality and latency vary; `llama3.1:8b` is the validated beta default and usually takes
  15-45 seconds per plan. A model outage or timeout fails the run with a stable synthesis code.
- The model sees the user message, workspace paths, registry metadata, and sampled column
  names/dtypes, but not source values. Prompt injection is constrained by the registry-derived
  JSON schema and the normal plan validator; adversarial prompts remain an ongoing test area.
- Natural-language conversations are process-local and bounded to 12 turns; they are lost on
  restart. Conversation persistence, background generation, inline source detection, and
  non-Ollama providers are v2 work.
- Operation roles are inferred from registry metadata: a transformation must require a
  pipeline DataFrame input and declare no side effects; a destination must declare side
  effects. Modules with unusual signatures need explicit role metadata later.
- API run state, results, in-memory logs, and the background scheduler are process-local. A
  restart loses active runs, stored API results, and logs.
- `RunManager` retains workflows, outcomes, and logs for the process lifetime; a retention or
  eviction policy is needed for long-running multi-run deployments.
- Source-only assessment and natural-language requests require an explicit `source` reference.
  A path mentioned only inside message text is not detected; inline intent detection is v2.
- Assessment runs synchronously during run creation and uses a full scan. Large sources can
  delay the response; bounded sampling, an assessment timeout, and background assessment are
  v2 work.
- Assessment results are not cached, and confirmation does not re-check the source content
  hash. Source changes between assessment and execution are caught only by normal execution
  validation; cache invalidation and stale-source checks are v2.
- The v1 confirmation flow accepts a destination but does not allow editing the draft
  transformations or choosing among multiple destinations; those are v2.
- Assessment artifacts are written below `artifacts/<run_id>/`. A pending or failed
  assessment can leave partial artifacts until the run is cancelled or cleaned up.
- API logs contain lifecycle and step events. Execution JSONL and transform CSV files are
  written per run; log rotation, concurrent writers, and cross-process locking are v2 work.
- Clarification runs can be continued with `POST /runs/{run_id}/messages`. The follow-up flow
  is single-process and cannot resume after a restart.
- `AGENT_ETL_API_KEY` optionally protects `/runs`; rate limiting and production auth
  hardening remain deployment controls.
- File destinations are atomic overwrite writers. Append mode, compression/encoding options,
  parent-directory creation, and cross-process file locking are v2 work (`LOD-2`).
- `PostgresTableLoader` is an adapter, not a plan destination. It requires an existing table
  and does not auto-create schemas/tables or map DataFrame dtypes (`LOD-3`). Registry execution
  still denies network access (`DB-2`).
- Load lineage, checksums, and load artifacts are not recorded yet; they follow with `LOD-5`.
  Monitoring records execution events but not per-load manifests.
- PostgreSQL sessions open one connection per session; connection pooling, pool exhaustion
  handling, and read-only database role grants are deployment concerns. Server-side batch
  iteration is implemented for source reads.
- `AGENT_ETL_DATABASE_SSLMODE=prefer` is the local default and does not verify certificates.
  Production deployments should use `verify-full` with `AGENT_ETL_DATABASE_SSLROOTCERT`.
- PostgreSQL integration tests start a temporary local cluster and skip when server binaries
  are unavailable. TLS tests use a short-lived OpenSSL-generated certificate and skip when
  OpenSSL is unavailable.
- JSON array readers materialize the document before chunking; use JSONL for large
  line-delimited sources. Parquet reads target one file, not partitioned datasets.
- Chunk manifests cover size, order, partial final chunks, total rows, hashes, and merge
  method. Profiling writes per-chunk records and validates sequence and schema during merge;
  resume or reload of partial/corrupt records is v2.
- PostgreSQL table reads are available through `PostgresSourceReader`; registry plans cannot
  select it yet because registry execution runs under a sandbox that denies network access.
  Add a configured-connection sandbox policy before binding database readers as plan modules.
- `pandas` is pinned to `3.0.6`; the local Windows code-integrity policy blocks pandas
  `3.1.0`'s unsigned `strptime` extension.
- `pyarrow` is required for Parquet reads.
- v1 profiling is full-source and retains exact numeric values and bounded maps in memory.
  Sampling, Parquet spill/external sort, declared quality rules, and per-column failure
  isolation are v2 work.
- Date statistics cover datetime-typed columns. Mixed-format date strings require a prior
  cast; naive and timezone-aware chunks are not merged silently.
- Accuracy remains blocked until a formula and reference rules are provided.
- Prompt injection and unsafe model output require continuous adversarial tests.

## Review gate

Architecture, security, and backlog were reviewed before implementation. Re-review them
before changing scope, security controls, or persistence guarantees. v2 candidates and
deferred edge cases are in `documents/backlog_v2.txt`.

`TST-1` remains partial: the beta has unit, integration, security, regression, golden
plan-shape, and optional live Ollama coverage, but not the full edge-case matrix. Promote the
remaining cases only when a real user flow needs them.
