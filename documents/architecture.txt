# Agent ETL Builder - Architecture

Version: 2.1
Status: beta 0.2.0b1; NL-1, API-2, MON-1, and BETA-1 implemented; TST-1 partial
Last updated: 2026-10-29
Scope: Module organization and runtime boundaries.

## Clean architecture

Dependency rule: source dependencies point inward. Domain code must not import
LangGraph, FastAPI, pandas, PostgreSQL drivers, or other infrastructure.

| Layer | Responsibility |
|---|---|
| domain/entities | Plans, registry entries, runs, assessments, artifacts, approvals, errors |
| application/use_cases | Assess sources, build/validate/execute plans, run the bounded workflow, profile, merge, load, cancel |
| application/validation | Plan validation policy: schema, registry, arguments, paths, limits, security, approval |
| application/registry | Allowlist specs, versions, constraints, examples, and side-effect policy |
| infrastructure/adapters | PostgreSQL sessions, files, LLM providers, local-memory run checkpoint, sandbox, logs |
| interfaces/API | FastAPI routes and request/response schemas |

V1 uses a process-local in-memory run checkpoint port (`RunCheckpointPort`). The current
adapter is `InMemoryRunCheckpoint`. The LangGraph `InMemorySaver` factory remains available
for a future graph-based workflow but is not wired into the composition root. Checkpoints
are lost when the process restarts. Multiple workers do not share checkpoints.

## Components and modules

- Module registry: approved functions, versions, inputs, typed constraints, outputs, side
  effects, and examples. The allowlist policy lives in `application/registry`; concrete
  callables are bound in `infrastructure/registry/bindings.py`.
- Plan builder/validator: schema, allowlist, operation roles, arguments, transformation
  contract, paths, limits, security, and approval. Policy checks live in
  `application/validation`; Pydantic parsing, plan size measurement, and filesystem probing
  are infrastructure adapters.
- Natural-language planner: `NaturalLanguagePlanIntake` implements `PlanIntakePort`. It binds
  source/destination operations deterministically from file extensions, samples a bounded
  source schema through `WorkspaceSourceSchemaProbe`, asks for missing paths, and calls a
  `PlanSynthesizerPort`. The beta adapter is `OllamaPlanSynthesizer`; it sends the message,
  paths, registry metadata, and sampled column names/dtypes to a local Ollama server. The
  model output is constrained by a JSON schema derived from the transformation registry, parsed
  into a `PlanDraft`, assigned step IDs, bound to the explicit I/O paths, and validated by the
  normal plan validator. Validation errors are fed back for bounded repair. No raw source values
  are sent. Background generation, inline path detection, full-schema planning, remote
  providers, and persistent conversations are deferred to v2.
- Source assessor: `AssessSourceUseCase` resolves a workspace file through a reader port,
  profiles the full source through `ProfileSourceUseCase`, and derives issues, assumptions,
  selected metrics, missing inputs, and a conservative draft plan. It runs under the sandbox
  runner. `AssessmentPlanIntake` runs it for source-only requests and for any
  `mode: "assessment"` request; assessment mode is read-only and ignores a supplied destination.
  Confirmation builds a validated `save_csv` pipeline plan and rejects a destination that would
  overwrite the source. Bounded sampling, inline intent detection, caching, draft editing, and
  database-backed assessment are deferred to v2.
- Interpreter: an application use case validates the plan, then orchestrates steps through
  a step-runner port; pandas and sandbox mechanics live in infrastructure.
- Sandbox: one serialized in-process execution guard. It confines file content access to
  the workspace (read-only runtime paths are allowed), denies network access, bounds
  wall-clock time, and checks the traced Python memory peak. It is not an OS-level
  container; native extensions and resources outside the patched Python APIs are not
  isolated.
- Database sessions: `DatabasePort` opens transaction-scoped read-only or writable sessions.
  `PostgresDatabase` implements it with psycopg, parameterized statements, TLS mode,
  connect/statement timeouts, commit-on-success, and rollback-on-error. `iter_batches`
  provides server-side cursors. Driver failures are mapped to `IngestionError` or `LoadError`
  with sanitized context.
- Ingestion adapters: read-only CSV, JSON, JSONL, Parquet, and PostgreSQL readers. File
  readers return DataFrames and expose ordered chunk iterators; JSON arrays are materialized
  before chunking, while CSV/JSONL/Parquet stream. `PostgresSourceReader` validates and quotes
  identifiers, uses read-only sessions, and streams server-side batches. Registry execution
  runs under a sandbox that denies network access, so PostgreSQL reads are adapter-level until
  a configured-connection sandbox policy is added.
- Ingestion identity: `source_id` is a canonical, credential-free hash; file content hashes
  use bytes, frame content/schema hashes support reproducibility, and `ChunkManifest`
  describes ordered chunks, partial final chunks, totals, and the merge method. Artifact names
  are sanitized and length-limited.
- Core profiling and chunk merger: `ProfileSourceUseCase` profiles ordered full-source chunks,
  writes one mergeable record per chunk, then merges counts, exact values/frequencies, and row
  fingerprints. `PandasChunkProfiler` owns pandas mechanics; domain types enforce metric,
  warning, and chunk-state invariants. Quality CSV, info JSON, and chunk JSON writers are
  filesystem adapters. Completeness, uniqueness, numeric/date/categorical statistics are
  explicit; consistency/validity rules, sampling, spill, and reports are v2 work. Accuracy is
  always `N/A`. Capped maps are marked approximate.
- Transformation DSL: the ordered plan step list is the v1 DSL. Ten allowlisted modules cover
  cleansing, casting, standardization, filtering, and imputation. Validation enforces operation
  roles, unique step IDs, idempotence, no transformation side effects, and cross-parameter
  semantics before execution. Source schema existence and dtype compatibility are still checked
  at execution time because the source schema is not part of the plan.
- Loaders: file destinations write to a temporary file in the target directory and atomically
  replace the final path. CSV, JSON, JSONL, and Parquet writers share the same mechanism and
  overwrite existing files. PostgreSQL loading is a transactional adapter with insert, upsert,
  and truncate-insert modes, validated/quoted identifiers, parameterized values, bounded batch
  sizes, and full rollback on batch failure. It requires an existing table and is not registered
  as a plan destination until a configured-connection sandbox policy exists (`DB-2`). Table
  creation, schema mapping, file append/compression, and load lineage are deferred.
- Monitoring: `JsonlRunLog` appends redacted lifecycle and step events to
  `logs/<run_id>.jsonl` while keeping redacted in-memory entries for the API.
  `CsvTransformLog` writes one row per transformation step to
  `artifacts/<run_id>/transform_log.csv`, neutralizes formula-like cells, and preserves the file
  during cleanup. Both adapters fall back to stderr if their file cannot be written. Log
  rotation, retention, and cross-process locking are deferred.
- State and lineage: local in-memory run checkpoints with plan, assessment, approval, hash,
  status, and error state. The API manager keeps execution results and conversation state in
  process memory. JSONL/CSV monitoring files persist on disk, but runs cannot resume after a
  restart. Full artifact lineage and load manifests remain `LOD-5`.
- Agent workflow: a plain application state machine, one instance per run. It selects
  assessment, natural-language, or submitted-plan intake; bounds clarification, validation,
  approval, execution, retry, cancellation, and cleanup; and resumes clarification through
  `POST /runs/{run_id}/messages`. External effects are ports; run snapshots are saved after
  every transition. LangGraph remains installed but is not wired into the runtime.
- Profiling artifacts: per-chunk records, `quality.csv`, and `info.json` are written below
  `artifacts/<run_id>/`. The source is never mutated. Metrics carry stable formulas and
  definition versions; `accuracy` is `N/A` until a formula/reference rules are supplied.
  Reports and sampling are deferred to the v2 backlog.
- API: FastAPI routes for run creation/status, assessment confirmation, clarification
  follow-ups, approval, cancellation, lifecycle/step logs, and health. A `RunManager` owns per-run workflow instances
  (each with its cancellation token), selects assessment or submitted-plan intake, schedules
  execution on a background thread pool, and keeps process-local outcomes and logs. Pydantic
  plan payloads are parsed by an infrastructure adapter; invalid plans are rejected before a
  run is created. Errors use a consistent envelope. Optional `AGENT_ETL_API_KEY` protection and
  a request-size limit are enforced by middleware.

## Run lifecycle

- States: `created`, `awaiting_clarification`, `ready`, `awaiting_approval`, `running`,
  `retrying`, `succeeded`, `failed`, `rejected`, `cancelled`, `timed_out`.
- Terminal states: `succeeded`, `failed`, `rejected`, `cancelled`, `timed_out`.
- A run stores its plan, plan hash, registry version, status, attempt count, approval state,
  clarification attempts, questions/missing inputs, error, timestamps, and an optional
  assessment report. `assessment_id` is derived from the attached report.
- Approval is required when the registry policy marks any operation as a write/destructive
  action, or when the plan explicitly requests it. The workflow waits with a configurable
  timeout; an approval timeout is a terminal `timed_out` state.
- Retries are bounded and exponential; only errors marked `retryable` are retried.
- Cancellation is checked before execution, between steps, after retry backoff, and while
  waiting for approval. A running step is bounded by the sandbox timeout.
- Cleanup runs on non-success terminal paths according to `AGENT_ETL_CLEANUP_POLICY`
  (`cleanup` removes `artifacts/<run_id>`; `retain` keeps partial output).
- The checkpoint port is process-local in v1; runs do not survive a restart.

## Data flow

1. User submits a request and source context.
2. Agent retrieves relevant registry entries and, for source-only requests, runs a
   read-only assessment first.
3. Validator checks schema, registry, arguments, paths, limits, security, and approval.
4. Required writes/DDL/destructive actions wait for human approval.
5. Interpreter executes the plan through adapters in a sandbox.
6. Profiling and transformation steps save per-chunk records.
7. Final chunk records are merged into quality/info artifacts and outputs; metrics never
   derive final averages or medians from per-chunk averages or medians.
8. Load and monitoring artifacts are written; lineage is saved.
9. API returns status, results, logs, and the next action.

## Source-only flow

1. Detect a source-only request: explicit `source`, no plan, and no destination.
2. Resolve a workspace-confined CSV, JSON, JSONL, or Parquet file and validate access.
3. Run a read-only full-source assessment and write only assessment artifacts.
4. Derive issues, candidate transformations, assumptions, selected metrics, and missing inputs.
5. Present the assessment and draft plan; keep the run in `awaiting_clarification`.
6. `POST /runs/{run_id}/confirm` supplies the destination, builds a `save_csv` pipeline plan,
   rejects source overwrite, and validates the plan before approval and execution.

Inline source paths in messages, bounded sampling, assessment timeouts, caching, draft editing,
source-change revalidation, and database-backed assessment are v2 candidates.

## Project layout

- `src/domain/` entities and contracts.
- `src/application/` use cases, ports, validation policy, and registry policy.
- `src/infrastructure/` PostgreSQL, file, LLM, local-memory run checkpoint, approval gateway,
  cleanup, clock, database sessions, ingestion readers and identifiers, assessment source
  reader/intake, profiling/artifact writers, deterministic/submitted plan intake, Pydantic
  schema and plan parser, filesystem probe, plan sizer/hasher, registry bindings, sandbox,
  background scheduler, run log, and logging adapters.
- `src/interfaces/` FastAPI routes and schemas.
- `src/main.py` composition root.
- `tests/` unit, integration, edge-case, and security tests.
- `documents/` specifications and decisions.
- `artifacts/<run_id>/` run outputs, transform logs, and core profiles. Reports are v2.
- `logs/<run_id>.jsonl` execution log.
- Root `README.md` and `pyproject.toml` before code starts.

## Module and file flow

- `interfaces/` receives requests and calls `application/` use cases.
- `application/` assesses sources, profiles and merges chunk records, builds and validates
  plans, then calls `infrastructure/` adapters through ports.
- `infrastructure/` reads/writes PostgreSQL and files, resolves assessment sources, profiles
  pandas chunks, writes quality and info artifacts, calls LLMs, checkpoints state, parses JSON
  plans, measures serialized plan size, probes the workspace, and runs sandboxed steps with
  workspace, network, time, and memory guards.
- `domain/` holds shared entities and validates core invariants.
- Plan validation and registry allowlists are application policy; Pydantic schemas,
  filesystem inspection, and concrete callables are infrastructure adapters.
- Run artifacts and logs are written under `artifacts/<run_id>/` and `logs/`.
- The registry, plan, transform log, and execution log are the boundaries between modules.
- The source-only branch uses `AssessSourceUseCase` through `AssessmentPlanIntake`; it writes
  only assessment artifacts, cannot write to the destination, and builds the executable plan
  only after `POST /runs/{run_id}/confirm`. `mode: "assessment"` always takes this branch.
